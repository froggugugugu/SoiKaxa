# SoiKaxa — PRD v4.1（2026-11-21）

名称: **SoiKaxa**（バスク語 Soinua Kaxa＝音の箱）。スリム版は **SoiKaxa Txiki**（txiki＝小さい）。識別子は `soikaxa` / `soikaxa-txiki`。

YouTube Music のプレイリストを Bluetooth スピーカーに流す、単体完結の小型専用端末。
操作はスマホ、本体は表示主体。外部サービスに依存しない。

> 旧案の経緯: ESP32 単体 → ESP32 + 自宅Pi中継 → Pi Zero 2 W 単体 → **Pi 4B 単体（現行）**。
> 理由は docs/DECISIONS.md を参照。

---

## 1. 結論サマリ

- 本体は手元の **Raspberry Pi 4B**。Wi-Fi・Bluetooth・YouTube Music の解決・A2DP 送信・表示用 LCD・ゲスト用 Wi-Fi AP を 1 台で賄う
- **外部サービス不使用**（Tailscale 等の中継なし）。「端末と USB 電源だけ持っていけば動く」
- 再生は **mpv + yt-dlp**（トランスコード不要）。プレイリスト一覧と公開コンテンツ検索は **ytmusicapi**（オーナーの認証を端末内に保持）
- **操作はスマホ**。端末自身が Wi-Fi AP を立て、LCD の QR → キャプティブポータルで設定画面／ゲスト画面が自動で開く
- 画面は **OSOYOO 3.5 インチ SPI LCD HAT（480×320、抵抗膜タッチ）**。曲名・次の曲・ゲスト QR を常時表示。タッチは「タップ＝再生/停止」「長押し＝次曲」のみ。物理ボタンなし
- **オープンソース前提で コア と ソースアダプタ を分離**。コアは YouTube を知らない
- 追加部材費は LCD 1 枚（約 2,000〜2,500 円）。Pi Zero 2 W 版（スリム版）は入手できたら microSD 移植で対応（任意）

### 最重要の設計判断

1. **MCU は ESP32 ではなく Linux ボード。** YouTube Music の認証・URL 解決（yt-dlp）・AAC/Opus デコード・A2DP Source を ESP32 単体で維持できない
2. **Zero 2 W を待たない。** 2026 年現在、供給不安定（公式代理店品切れ、Amazon 転売 2 万円）。ソフトは共通なので後から移植可能
3. **タッチ UX にコストをかけない。** DSI/静電容量タッチ（5,000〜9,000 円）は見送り。操作はスマホに寄せる
4. **YouTube の変更追従は端末内で完結。** yt-dlp を週次自動更新

## 2. 目的・ユーザー

**目的**: スマホを常時使わず、電源をつなぐだけで自分の YouTube Music プレイリストが Bluetooth スピーカーから流れる小型専用機。会場に持ち込み、友人が QR を読むだけで曲を追加できる。

**想定ユーザー**
- オーナー（自分）: 自宅・書斎・ガレージ・パーティ会場
- ゲスト（友人・家族）: アプリ不要、アカウント不要、QR を読むだけ

## 6. ユーザー体験

### 6.1 オーナーの会場設置（目安 3 分）

前提: 自宅で初期設定済み（YouTube 認証、オーナー PIN、自宅 Wi-Fi、自宅スピーカー）。

1. 電源をつなぐ。LCD「起動中…」→ 既知 Wi-Fi がないので端末は AP（`soikaxa-XXXX`）を立てる。LCD:「スマホでこの QR を読んでください」＋ Wi-Fi 参加 QR
2. QR を読む。スマホが端末 AP に入り、ポータル画面が自動で開く。「オーナーはこちら」→ PIN
3. 会場 Wi-Fi を登録。スキャン一覧から選ぶ／手入力（ステルス）／貼り紙を撮影して取り込む
4. 端末が会場 Wi-Fi に接続。AP は出したまま。LCD:「インターネット接続 OK」→ 自動でゲスト用 QR 画面へ
5. スピーカーをつなぐ。会場の BT スピーカーをペアリングモードにし、設定「スピーカー」→ スキャン → 選択。自宅スピーカーなら自動再接続
6. 「マイプレイリスト」から選んで再生。LCD: 曲名＋ゲスト QR。スマホは端末 AP から離れてよい

パーティ中: 本体タッチで再生/停止・次曲。スマホ（PIN）で音量・キュー並替/削除・ゲスト受付停止・スピーカー切替。撤収は電源を抜くだけ。会場 Wi-Fi は記憶され、次回は手順 3〜4 が省略される。

### 6.2 友人が曲を流す（目安 30 秒）

1. 「端末の QR 読んで」と言われ、カメラをかざす。「ネットワーク “soikaxa-XXXX” に接続」をタップ
2. ゲスト画面が自動で開く（Wi-Fi 同意画面と同じ仕組み）。名前を任意入力
3. 検索 → 公開プレイリスト・曲 → 「キューに追加」または「この次に流す」
4. LCD:「次：○○（A さん）」。今の曲が終わると流れる
5. もう一度操作したければ QR を読み直すだけ。一度入ったスマホは次から QR なしでつながる

裏で起きていること: ゲストのスマホはインターネットに出ない。検索も再生も端末が会場 Wi-Fi 経由で行う。ゲスト画面はポータルの簡易ブラウザ内で完結する設計（カメラ API・プッシュ通知に依存しない）。

### 6.3 トレードオフ（外部サービスを使わない代償）

- オーナーの 5G からの遠隔操作は不可。操作は AP の届く範囲限定
- ゲストのスマホは一時的に端末 AP につながる。iPhone は「インターネットなし」の Wi-Fi を自動で離れることがあるため、操作はポータル内で短く済ませる
- 遠隔操作が欲しくなったら、自宅 Pi に WireGuard を立てて端末を常時接続させる（v2、自前・ポート開放と DDNS が必要）

## 7. 技術的制約と設計判断

| 制約 | 事実 | 判断 |
| --- | --- | --- |
| YouTube Music アクセス | 公式の再生ストリーム API はない。yt-dlp 相当の解析（頻繁に仕様変更）とアカウント認証が必要 | Python が動く Linux ボード。yt-dlp は端末内で週次自動更新 |
| Bluetooth 送信 | A2DP Source は Bluetooth Classic が必要 | Pi 4B 内蔵 BT で BlueZ が A2DP Source 対応 |
| コーデック | YouTube 配信は AAC/Opus | mpv がそのまま再生 |
| Wi-Fi 同時動作 | STA と AP は同一チャンネルでないと同時動作しない | NetworkManager で AP チャンネルを STA に追従 |
| 起動時間・電力 | Linux 起動 20〜30 秒、消費 3〜4W | 最小 OS・不要サービス停止・LCD で起動中表示 |

### 採用しなかった案

- **ESP32 単体**: 認証・署名解読・AAC デコードを全部ファームで抱え、YouTube 側の変更のたびに書き換え。保守不能
- **ESP32 + 自宅 Pi 中継**: 自宅サーバーがないと動かず「持っていけば OK」にならない
- **Tailscale / Funnel**: 体験は良いが外部サービス依存。端末 AP 方式で代替
- **DSI / DPI 静電容量タッチ（HyperPixel 等）**: UX は上がるが 5,000〜9,000 円。操作はスマホに寄せる方針で不要
- **Orange Pi Zero 2W / Radxa Zero 3W**: 安いが技適のないものが多い

### サービス規約・将来性

yt-dlp 経由の取得は YouTube 利用規約に抵触する可能性がある。個人利用に限定。ソースアダプタを差し替え可能にし、配布版は Spotify 等の公式 API を前提にする。

## 8. システム構成

```
[YouTube Music] --HTTPS(会場Wi-Fi/テザリング)--> [Pi 4B 端末] --Bluetooth A2DP--> [BT スピーカー]
                                                    ^   ^
                       オーナーのスマホ (PIN) --------+   +-------- 友人のスマホ (検索・キュー追加)
                                 LCD の QR → 端末 AP (soikaxa-XXXX) に参加 → キャプティブポータル
```

| コンポーネント | 役割 | 実装 |
| --- | --- | --- |
| Pi 4B 本体 | 上流 Wi-Fi（STA）、自分の AP、YouTube Music 認証・取得・検索、URL 解決、再生、A2DP 送信、LCD、Web サーバー、キャプティブポータル | Raspberry Pi OS Lite 64bit + Python デーモン + mpv + yt-dlp + ytmusicapi + BlueZ + PipeWire + NetworkManager + dnsmasq |
| 3.5 インチ SPI LCD HAT（480×320） | 設定用 QR / 曲名とゲスト用 QR / エラー案内。タッチは再生/停止・次曲 | OSOYOO、fbtft、PIL + qrcode |
| オーナーのスマホ | 会場 Wi-Fi 登録、プレイリスト選択、スピーカー、キュー管理、音量 | 端末 AP 経由の単一 HTML、PIN |
| ゲストのスマホ | 公開コンテンツ検索・キュー追加 | 同じ HTML のゲストビュー、アプリ・アカウント不要 |
| BT スピーカー/イヤホン | 出力 | 市販品、A2DP 対応なら何でも |

### 8.1 コアとソースアダプタの分離

| 層 | 内容 | リポジトリ | ライセンス |
| --- | --- | --- | --- |
| コア | 再生エンジン（mpv）、キュー、Bluetooth、AP/ポータル、Web アプリ、LCD、タッチ、アダプタインターフェース | `soikaxa` | MIT または Apache-2.0 |
| アダプタ: ローカル MP3 | microSD 内のフォルダをプレイリストとして列挙。オフラインフォールバック | コアに同梱 | 同上 |
| アダプタ: ネットラジオ | 局の URL リストをプレイリストとして扱う | コアに同梱（v2） | 同上 |
| アダプタ: YouTube Music | ytmusicapi + yt-dlp。自分のアカウントで自己責任で使う旨を README に明記 | `soikaxa-adapter-ytmusic` | 同上 |
| アダプタ: Spotify（将来） | 公式 Web API + librespot（Premium 必須） | 別リポジトリ | 同上 |
| Amazon Music | **不可**。第三者向け再生 API がなく Widevine DRM | — | — |

アダプタインターフェースは 4 つだけ:
`list_playlists()`, `list_tracks(playlist_id)`, `search(query)`, `resolve(track_id) -> 再生可能な URL またはパス`。
コアはこれを mpv に渡すだけ。

命名: プロジェクト名・README・SSID に「YouTube」「yt」を含めない。mpv/BlueZ は GPL だが別プロセスとして呼ぶのでコアのライセンスに伝播しない。認証情報・Cookie はコミットしない。DRM 回避は行わない。

## 9. ソフトウェア構成

| モジュール | 役割 | 技術 |
| --- | --- | --- |
| OS | 最小構成、読み取り専用ルート（overlayfs）、設定は別パーティション | Raspberry Pi OS Lite 64bit (Bookworm) |
| ネットワーク | STA（上流）と AP（`soikaxa-XXXX`）の同時動作、複数 SSID 自動選択、ステルス SSID 対応 | NetworkManager（nmcli）、AP は STA と同一チャンネル。内蔵チップで AP を兼ねる場合、上流は 2.4GHz に限る（5GHz の DFS チャンネルでは AP を開始できない／屋外利用。2026-11-22 決定） |
| キャプティブポータル | AP に入ったスマホに自動で Web 画面を開かせる（iOS/Android の接続検知 URL に応答） | dnsmasq + FastAPI のリダイレクト |
| Web アプリ | ゲストビュー / オーナービュー（PIN）、Wi-Fi 登録、スピーカー、キュー、音量 | FastAPI + 単一 HTML（外部 CDN 不使用、ポータル簡易ブラウザで動く） |
| ソースアダプタ | 4 関数 I/F | Python Protocol |
| 再生エンジン | キュー優先の連続再生、次曲先読み | mpv（--no-video、yt-dlp 連携、JSON IPC） |
| Bluetooth | A2DP Source、記憶機器へ自動再接続、設定画面からスキャン/ペアリング | BlueZ + PipeWire |
| LCD | 状態別画面（起動中 / 設定 QR / 曲名+ゲスト QR / エラー）、タッチ判定 | fbtft (/dev/fb1)、PIL + qrcode、evdev |
| 制御デーモン | 状態機械、キュー、ウォッチドッグ | Python、systemd |
| 自動更新 | yt-dlp を週次更新、失敗時は前バージョン維持 | systemd timer |

状態機械: `BOOT → AP_ONLY（上流未接続、設定 QR 表示）→ ONLINE → BT_CONNECTING → IDLE → PLAYING → ERROR`。AP は全状態で常時 ON。

### 9.1 初回設定フロー（自宅、一度だけ）

1. 電源 ON。LCD に設定用 QR（`WIFI:T:WPA;S:soikaxa-XXXX;P:xxxx;;`）。スマホで読むと端末 AP に接続し、ポータル画面が開く
2. オーナー PIN を設定
3. 自宅 Wi-Fi とスマホテザリングを登録。端末が上流に接続
4. YouTube Music 認証: 画面の案内に従い、スマホブラウザで YouTube Music にログインした状態の認証ヘッダを貼り付けて登録（ytmusicapi の browser 方式、一度だけ）
5. プレイリスト一覧から既定を選ぶ
6. BT スピーカーをペアリングモードにし、「スキャン」で選ぶ
7. 「電源 ON で自動再生」を有効にして完了

認証情報は端末内の microSD に残る。設定画面に「認証削除」ボタンと、タッチ長押しからの初期化を用意する。

### 9.2 Wi-Fi 入力仕様

| 経路 | 内容 | 実装 |
| --- | --- | --- |
| 一覧から選ぶ | スキャン結果をタップ。ステルス SSID は出ない | `nmcli dev wifi list` |
| 手入力 | 「一覧にない/ステルス」で SSID 欄とステルストグルを表示 | 接続時に `hidden=yes` |
| 写真から取り込む | ① 入力欄で iOS キーボードの「テキストをスキャン」（Live Text）。② 貼り紙が Wi-Fi QR なら「QR を撮影」→ 撮影画像を端末側 JS で解読し自動入力。③ クリップボードから貼り付け | ① は標準 input で実装ゼロ。② は `<input type=file accept=image/* capture=environment>` + jsQR（ポータル内では getUserMedia が使えないため撮影→解読方式） |

長い文字列を壊さない入力欄: `autocorrect=off` `autocapitalize=off` `spellcheck=false`。パスワードは「表示」トグル付きで既定表示。保存前に文字数付きで確認表示。接続失敗時は「パスワード違い」「ステルス未指定」「キャプティブポータル」を分けて案内。保存後は会場名（既定は SSID）付きで記憶し、次回自動接続。

### 9.3 操作仕様（本体: タッチのみ）

| 操作 | 動作 |
| --- | --- |
| 画面タップ | 再生/停止トグル |
| 画面長押し（1.5 秒） | 次曲 |
| 画面長押し（10 秒） | 設定用 QR を全面表示 |

音量・プレイリスト選択・スピーカー切替・キュー管理・初期化はスマホ側（オーナー PIN）。誤タッチ防止に 0.3 秒以上の接触で判定。

### 9.4 LCD 画面仕様（480×320）

| 状態 | 表示 |
| --- | --- |
| 起動中 | 「起動中…」と進捗バー |
| 上流未接続 | 「スマホでこの QR を読んでください」＋設定用 QR（左半分に大きく） |
| 通常 | 左: ジャケット写真入りのレコードが回転（9.5 参照）。右: 今の曲 / アーティスト / 進捗 / 次の曲（追加者名）/ ゲスト用 QR（静止） |
| エラー | 原因を一言（「Wi-Fi に繋がりません」「この Wi-Fi は同意が必要。テザリングへ」「スピーカーが見つかりません」）と設定 QR |

SPI の描画速度（数 fps）で十分な静的表示を基本とし、動かすのは回転レコードの円盤だけ。バックライトは PWM で調光。

### 9.5 UI デザイン: サイバー系モチーフと回転レコード（2026-11-21）

再生中は左半分でジャケット写真入りのレコードがゆっくり回る（1 回転約 9 秒）。右半分は曲名・次の曲・ゲスト QR を静止表示。

| 項目 | 仕様 |
| --- | --- |
| 配色 | 背景 #0B0F14、主色シアン #5DCAA5、差し色マゼンタ #ED93B1、文字はグレー系。夜はバックライトを PWM で落とす |
| フォント | 等幅。欧文 JetBrains Mono、和文 Noto Sans Mono CJK JP |
| レコード | 直径 200 px。外周シアン細線と溝の同心円、中央にジャケット写真を円形切り抜き（直径 104 px）、マゼンタの弧 1 本で回転を見せる |
| ジャケット写真 | ytmusicapi の曲サムネイル URL から取得し端末内キャッシュ。無い曲はプレイリスト名から生成した幾何模様 |
| 回転の実装 | 曲切替時に 5° 刻み 72 フレームを PIL で事前生成（RGB565、約 5.8 MB）。再生中は 200×200 領域だけ /dev/fb1 に書く（目標 8 fps）。生成中は静止画 |
| 一時停止時 | 回転を止める |
| 曲切替時 | 2〜3 フレームのグリッチ風トランジション（任意） |
| QR | 常に静止、白地に黒、再描画しない（読み取り性優先） |
| スマホの Web 画面 | 同じ配色・フォント。レコードは CSS アニメーションで 60 fps |

## 13. リスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| STA+AP+A2DP の同居で音切れ | 体感品質 | フェーズ 1 で判定。AP はゲスト操作専用で帯域を使わない。ダメなら USB Wi-Fi ドングルを AP 専用に追加 |
| キャプティブポータルが自動で開かない OS バージョン | ゲストが迷う | LCD に `http://10.42.0.1` も併記。ポータル検知 URL（Apple/Google/Microsoft）を網羅 |
| iPhone が「インターネットなし」の端末 AP を自動で離れる | 操作途中で切れる | ゲスト操作をポータル内で短く完結させる。オーナーは「このネットワークを使用」を選ぶ |
| 起動が遅い（30 秒超） | 体験が損なわれる | 最小 OS、不要サービス停止、LCD で起動中表示 |
| yt-dlp が YouTube 側の変更で動かなくなる | 再生不能の期間 | 端末内で週次自動更新。ローカル MP3 をフォールバックソースに |
| YouTube 利用規約の問題 | 配布・キット化ができない | 個人利用に限定。ソースアダプタを差し替え可能に |
| ゲストの悪ふざけ（大量追加・不適切な曲） | 場が荒れる | 1 人あたりキュー上限、オーナーの削除・受付停止、追加者名表示 |
| 電源ブチ切りで microSD 破損 | 起動不能 | overlayfs、設定は別パーティション |
| 密閉ケースでの発熱 | サーマルスロットル | ヒートシンク + 放熱スリット、CPU クロック上限を下げる |

### 13.1 YouTube 側の仕様変更への追従運用（2026-11-07 追加）

実態: プレイリスト取得・検索（ytmusicapi）は年 1 回程度、再生 URL 解決（yt-dlp の `resolve`）が年 2〜5 回、数時間〜数日止まる。これを許容し、以下で吸収する。

1. yt-dlp を **nightly チャンネルで毎日自動更新**。失敗時は前版を維持
2. **Deno を導入**（aarch64 公式バイナリ）。署名解読の成功率を上げる
3. **毎朝のヘルスチェック**: 既知の曲 1 つを resolve し、結果を LCD とオーナー画面に表示（「YouTube 側の変更で停止中。更新待ち」）
4. オーナー画面に「今すぐ更新」ボタン
5. 停止中は **ローカル MP3 / ネットラジオアダプタに自動フォールバック**（パーティ本番で沈黙しない）
6. 次曲の先読みは 1 曲分だけ。リクエストを増やさずアカウントのボット判定リスクを下げる

フェーズ 5（堅牢化）の受け入れ条件に「resolve 失敗時にローカル MP3 へ自動で切り替わる」を含める。
