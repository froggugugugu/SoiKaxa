## 指摘事項

### MUST(必須修正・確定のみ)

- [ ] **[spec-quality]** `core/soikaxa/bootstrap.py:138` 監視ループがキャプティブ判定の文言をすぐに消してしまい、FR-015 の受け入れ基準を満たさない。
  **理由**: `_monitor` は `connect_network(rt)`(L138)を呼んだ直後に health.json を読む。captive の場合、`connect_network` は `health_notice` にキャプティブ文言を入れて FAIL を送る(L103-105)。しかし L142-143 で `res.ok` なら `health_notice = ""` に上書きされる。毎朝の health timer があるので、実機では ok の health.json が存在するのが普通。その結果、30 秒ごとの周回で状態は ERROR のまま文言だけが消え、LCD には `render_error(self.error_message or st.notice or "エラー")`(`lcd/controller.py:115`)により「エラー」とだけ表示される。逆に health.json が無い環境では、上流がオンラインに戻ってもキャプティブ文言が消えない(online 分岐 L101-102 と Wi-Fi 登録成功時 `web/app.py:395-396` のどちらでもクリアしない)。PRD_001 FR-015 は「この Wi-Fi は同意が必要。テザリングへ」の表示を求めている。
  **修正案**: ネットワーク由来の通知とヘルスチェック由来の通知を別のフィールドに分ける(例: `net_notice` / `health_notice`)。`connect_network` は online / offline の分岐で `net_notice` を消し、`status().notice` は fallback > net > health の優先順で合成する。回帰テストを `tests/test_controller_bootstrap.py` に 2 件足す: 「captive の後に ok の health.json があっても文言が残る」「online に戻ると文言が消える」。

- [ ] **[security / HIGH]** `core/soikaxa/web/app.py:262` PIN が未設定の間は、誰でも先にオーナーを名乗れる。この状態は初回起動時と初期化後に生じる(OWASP A07/A01, CWE-306 / CWE-367)。
  **理由**: `/api/owner/setup`(L262-267)は認証なしで動き、`owner_pin_hash is None` なら PIN を保存してセッションを発行する。PIN が None になるのは次の 2 つの場面。(1) 初回起動時。(2) `/api/owner/reset`(L498 `store.reset()`)の後。`config.py:137-142` の reset は ap_ssid / ap_password を残すため、それまでに AP に入ったゲストはそのまま再接続できる。AP の QR は再生中の LCD に常に表示されている(`controller.py:127`、`screens.py:103-104`)ので、AP パスワードは事実上その場の全員が知っている。さらに `index.html:246,255` は has_pin=false のとき、どの来訪者にも「最初にオーナー PIN を決めてください」と表示する。上流ネットワーク側からも到達できる(SHOULD の 0.0.0.0 待ち受けの指摘を参照)。確認(L264)と保存(L266)がアトミックでないため、同時に送られると後勝ちになり、両方にセッションが発行される。乗っ取られた場合は、AP パスワードの閲覧と再生成、Wi-Fi の追加と削除、音源認証の登録と削除、初期化までできる。
  **修正案**: setup の条件に「その場に物理的にいること」を加える。例えば、起動時と reset 時にワンタイムのセットアップコードを生成して LCD のセットアップ画面(`render_setup`)にだけ表示し、`PinIn` に `setup_code` を追加して `secrets.compare_digest` で照合する。あるいは、本体のタッチ操作(`Gesture.SETUP_QR`)から 60 秒間だけ setup を受け付ける。reset 時は AP パスワードも再生成する(`generate_ap_credentials` を呼んで `start_ap`)。PIN の確認と保存は SettingsStore のロック内で 1 回の操作にまとめる。修正難易度は中。

### SHOULD(推奨修正)

#### spec-quality
- [ ] `core/soikaxa/bootstrap.py:144` IDLE / PLAYING / AP_ONLY の間は Bluetooth の切断を検知せず、再接続もしない。**理由**: `connect_speaker` が呼ばれるのは ONLINE / BT_CONNECTING のときだけ(L144-149)で、BT_LOST を送るのは `connect_speaker` の中(L120)だけである。そのため `state.py:44,46` の BT_LOST 遷移は実際には通らない。FR-006 は記憶機器への自動再接続を求めている。**修正案**: IDLE / PLAYING / AP_ONLY でも BT_POLL_SEC ごとに `rt.bt.is_connected(known[0].mac)` を確認し、切れていれば BT_LOST を送って再接続する。スピーカー側から自動接続されるかどうかを実機で確かめてから判断してもよい。
- [ ] `core/soikaxa/state.py:46` PLAY は IDLE からしか遷移しないため、音が鳴っていても状態が PLAYING にならない場合がある。**理由**: 次の 3 つのケースで起きる。AP_ONLY での autoplay(`bootstrap.py:116-118`)、PLAYING → BT_LOST → BT_CONNECTED で IDLE に戻る経路、ERROR → NET_UP の経路。このとき LCD は設定画面またはエラー画面のままで、レコードも回らない(`controller.py:168`)。`daemon.py:304` は `dispatch(Event.PLAY)` の戻り値を見ていない。**修正案**: 再生中かどうかの判定を `status().now is not None and not paused` に切り離す。あるいは、`_current` があるときは PLAYING に入る遷移を足す。状態遷移のテストを `test_daemon.py` に追加する。
- [ ] `core/soikaxa/lcd/controller.py:178` 1 秒ごとの全面再描画でレコードが 0° に戻り、毎秒カクつく。**理由**: `screens.py:82` が回転していない `self._disc` を貼るため。毎秒 `make_qr` を作り直していることも、PRD §6 の「QR は静止させ、再描画しない」に反する。**修正案**: 全面再描画のときは現在フレームを peek して貼る。あるいは進捗の矩形だけを部分書き込み(`write_raw`)する。
- [ ] `core/soikaxa/net.py:211` 保存済みの SSID を登録し直して失敗すると、正常に動いていた接続プロファイルまで消える。**理由**: 最初に `nmcli connection delete` を実行し、up に失敗すると新しく作ったプロファイルも削除する(L237-238)。`wifi_labels` には古いエントリだけが残る。**修正案**: 一時的な名前で add → up し、成功したら旧プロファイルを delete して rename する。失敗したら一時プロファイルだけを消す。この挙動をテストに追加する。
- [ ] `core/soikaxa/bootstrap.py:90` 既定の設定(AP と STA が同じ wlan0)では、STA に接続すると AP の接続が落ちる見込みが高い。**理由**: NetworkManager は 1 つのデバイスで同時に 1 つの接続しか有効にできない(`net.py:236` と `net.py:317` が互いの接続を落としうる)。PRD_001 R-01 で、実機フェーズ 1 の判定対象になっている。**修正案**: `02_verify.sh` で同時動作できるかを判定する。不合格なら、`01_setup.sh` で `uap0` を作成し、`SOIKAXA_AP_IF=uap0` を設定する。結果は `docs/phase1-results.md` に記録する(実機確認待ち)。
- [ ] `adapters/soikaxa-adapter-ytmusic/soikaxa_adapter_ytmusic/__init__.py:185` 検索結果のプレイリストが、曲数の上限によって常に切り捨てられる。**理由**: songs を limit(20)件まで取得してからプレイリストを後ろに追加し、`out[:limit]` で切っている。そのためゲスト向けのプレイリスト展開 API(`web/app.py:226-233`)がほぼ使えない。**修正案**: プレイリストの枠を先に確保する(`tracks[:limit - len(pls_out)] + pls_out`)。20 曲とプレイリストの両方が返るケースのテストを追加する。
- [ ] `output/prd/PRD_001_soikaxa.md:112` PRD §5 の Settings にある `brightness` が、実装(`config.py:56-71`)にも `docs/data-model.md:11-27` にも無い。**修正案**: v1 で不要なら PRD から外し、必要なら Settings と data-model に追加する。どちらにするかは PRD の更新として決める。

#### security
- [ ] `core/soikaxa/bootstrap.py:212` [MEDIUM] HTTP が `0.0.0.0` で待ち受けているため、上流(STA)側からも到達できる。Host ヘッダの検査(`portal.py:34-40`)はクライアントが自由に偽装できるので、アクセス制御として機能しない。`<nodename>.local` も mDNS で名前解決される(CWE-1327 / CWE-346)。**修正案**: 待ち受けを `10.42.0.1` に限定する。あわせて、`request.client.host` が `10.42.0.0/24` 内かを確認するか、nftables で STA 側の tcp/80 を遮断する。ARCH §12 の脅威モデルに「上流ネットワークの第三者」を追記する。
- [ ] `core/soikaxa/web/app.py:275` [MEDIUM] ロック中でも、未認証のリクエストで scrypt(約 16MiB、数十 ms)が先に計算される。同時実行数にも上限がない(CWE-400 / CWE-770)。**修正案**: `verify_pin` より前に `pin_guard.check()` を呼ぶ。scrypt の同時実行数を `BoundedSemaphore(2)` などで制限し、空きが無ければ 429 を返す。
- [ ] `core/soikaxa/auth.py:63` [MEDIUM] 失敗回数を端末全体で 1 カウンタだけで数えており、ロック時間も固定の 300 秒である。そのため、ゲストがオーナーを締め出し続けられる。4 桁 PIN は約 83 時間で総当たりされる(CWE-645 / CWE-307 / CWE-521)。**修正案**: PIN の最小桁数を 6 にする。ロック時間を指数的に延ばす。本体のタッチ操作からログインできる復旧経路を用意する。
- [ ] `adapters/soikaxa-adapter-ytmusic/soikaxa_adapter_ytmusic/__init__.py:178` [MEDIUM] ゲストの検索とプレイリスト展開が、オーナーの認証済み YouTube セッションで実行されている。回数制限も件数の上限もない(`get_playlist(limit=None)` L157)(CWE-770 / CWE-359)。**修正案**: 検索とゲスト向けの展開には未認証の `YTMusic()` を使う。`/api/search` 系に sk_gid と IP 単位のレート制限をかけ、展開する件数に上限を設ける。
- [ ] `systemd/soikaxa@.service:10` [MEDIUM] ネットワークに公開するデーモンが、sudo を使えるログインユーザーで動いている。systemd のサンドボックス設定も一切ない(CWE-250 / CWE-269)。**修正案**: `NoNewPrivileges` / `ProtectSystem=strict` / `ReadWritePaths=/var/lib/soikaxa` / `ProtectHome=read-only` / `PrivateTmp` / `CapabilityBoundingSet=CAP_NET_BIND_SERVICE` / `RestrictAddressFamilies` などを追加する。可能なら専用ユーザーで動かし、venv は root 所有にする。
- [ ] `core/soikaxa/web/app.py:85` [MEDIUM](既知・受容済みの再掲)PIN と Cookie が平文の HTTP で流れており、Cookie に Secure 属性もない。AP の PSK は LCD に常に表示されている(CWE-319 / CWE-614)。**修正案**: PIN を他のサービスと使い回さないよう UI で注意する。オーナーセッションの有効期限を短くする。ゲスト用の QR と管理用の QR を分ける。WPA3-SAE を検討する。
